# AGENTS.md

Guide for anyone — person or agent — working on **Parcelas Customizadas para WooCommerce**
(*Custom Installments for WooCommerce* in English), the free WooCommerce plugin distributed on
WordPress.org, and its commercial companion
[`wc-custom-installments-pro`](../wc-custom-installments-pro).

Read this before editing anything. The plugin's hardest constraints are not visible from a single
file.

---

## 0. Rules that override preference

1. **Code is written in English; what the store owner reads is written in Brazilian
   Portuguese.** Identifiers, comments, docblocks, `translators:` notes, commit messages and
   documentation are English. Every user-facing string — PHP and Vue alike, the plugin header and
   `readme.txt` included — is authored in pt-BR inside `__()` / `wp.i18n.__`, and every other
   language is a translation of it. English ships as a bundled en_US catalogue (see §8), because
   translate.wordpress.org has no English (United States) locale to deliver it. A new string needs
   its en_US entry in the same change.
2. **Some names cannot change.** See §5. A rename there silently destroys customer data or content.
3. **The gate is one function.** Never add a second place that decides whether a paid feature runs.
4. **Nothing contacts an external server without a person asking.** See §6.
5. **Match the surrounding code.** Tabs in PHP, `array()`, spaces inside parentheses, two blank
   lines between methods, a docblock on every class and public method.
6. **Do not commit or push unless asked.**
7. **Commit messages are English, Conventional Commits, and carry no attribution.** Write
   `type(scope): summary` in the imperative, as the history does (`fix(admin): …`,
   `feat(compat): …`), with a body explaining *why* when the change is not obvious. Never add
   `Co-Authored-By`, "Generated with …", or any other co-authorship or tool-attribution line — not
   in commits, pull requests, the changelog or the code.
8. **The admin UI is built from components, never hand-written HTML.** See §7. Vue 3 is the
   framework; do not bring a second one into the bundle.

## 1. What this is

A WooCommerce plugin that answers the question a shopper asks before buying: *how much is it per
month, and what do I save by paying it all at once?* It renders an instalment plan and an
upfront-payment discount under the product price, on the shop loop and the product page, plus the
payment methods the store accepts.

It replaces `woo-custom-installments` 5.x, which was a single paid plugin. This is a free plugin
with a paid add-on, and §5 exists because the 5.x installed base has to survive the move. The
version numbering continues from 5.x: the first release of this codebase is **6.0.0**, and `@since`
on new code is the version about to ship.

### Name and slug

The display name is **Parcelas Customizadas para WooCommerce**, the name the 5.x installed base
already knows. Like every other string it is authored in pt-BR and translated: the bundled en_US
catalogue turns it into *Custom Installments for WooCommerce*.

The slug and text domain are `wc-custom-installments`, and they are not negotiable:

- WordPress.org no longer accepts new slugs starting with `woo`; it requires `wc` instead.
- The text domain of a WordPress.org plugin must equal its slug.
- 5.x was never on WordPress.org, so there is no existing `woo-custom-installments` listing to
  inherit. It updated from MeuMouse's own server.
- A display name must not start with a trademark, which rules out "WooCommerce …" and "WC …".
  "… para WooCommerce" at the end is the accepted form.

WordPress.org derives the slug from the display name on submission
(`parcelas-customizadas-para-woocommerce`). Ask the reviewers for `wc-custom-installments` when
submitting.

| | Free | Pro |
|---|---|---|
| Slug and text domain | `wc-custom-installments` | `wc-custom-installments-pro` |
| Namespace | `MeuMouse\WC_Custom_Installments\` | `…\WC_Custom_Installments\Pro\` |
| Constants | `WC_CUSTOM_INSTALLMENTS_` | `WC_CUSTOM_INSTALLMENTS_PRO_` |
| Hooks | `WC_Custom_Installments/…` | `WC_Custom_Installments/Pro/…` |
| REST | `wc-custom-installments/v1` | same namespace, routes registered by the add-on |
| Licence | none | MDS SDK against `cloud.meumouse.com` |

Requires PHP 8.1, WordPress 6.5, WooCommerce 8.0.

## 2. Layout

Backend PHP lives entirely under `admin/`, Composer included. Frontend lives entirely under `app/`.
The root holds the bootstrap file, the docs, the build scripts and the directories WordPress
expects. Both `admin/vendor/` and `app/dist/` are generated by the build and are not versioned.

```
wc-custom-installments.php   Bootstrap: autoloader, Core\Init
admin/src/
  Admin/                     Menu, Default_Options, Product_Settings, Settings\*, Onboarding\*
  Api/ Assets/               Extension surface; Vite manifest resolution and enqueueing
  Campaigns/                 Post_Type, Rules, Repository (and its index), Resolver, Scheduler
  Compatibility/             Hook_Aliases and the 5.x bridges
  Core/                      Init, Features, Functions, Scripts, Helpers, Logger, Migrator, Onboarding
  Engine/                    Calculate_Installments, Calculate_Values, Product_Config
  Frontend/                  Render_Elements, Components, Styles, Shortcodes, Element_Registry, Templates
  Integrations/              Themes, Elementor, pricing plugins
  Rest/                      Abstract_Route + one class per endpoint
  Views/                     The page shells the Vue apps mount into
app/src/
  entries/                   One per screen: settings, campaigns, onboarding, addon-page, storefront
  components/ composables/ pages/ utils/ styles/
  storefront/                The shop-side runtime: no framework, no jQuery of ours
languages/                   Node i18n pipeline
scripts/                     build, version, lint-php, env, generate-*-docs
tests/                       Standalone harnesses: no PhpUnit, no WordPress, no database
```

### Class discovery

`Core\Init` is the only class the plugin file constructs. Everything else is read from the Composer
classmap and instantiated on the hook its namespace implies. A new class is wired up by living
under `admin/src` with the right namespace and a **constructor taking no required arguments**.

`Init::is_discoverable()` is the one rule, public and static because the Pro add-on hands its own
classes to the same pass. Anything under a `\Widgets\` namespace is skipped: a page-builder widget
is constructed by its own manager, and building a second unregistered copy surfaces as a fatal in
somebody else's code.

After adding, renaming or moving a class: `cd admin && composer dump-autoload -o`.

## 3. The feature gate

`Core\Features::is_available()` is the single place deciding whether a paid capability runs. A
settings field names the feature that gates it, and three behaviours follow from that one key:

1. The field ships to the browser marked `locked`.
2. `Settings\Repository` refuses to persist it.
3. The engine asks before applying the behaviour.

**Never check a licence anywhere else.** The Pro add-on answers one filter,
`WC_Custom_Installments/Features/Is_Available`, and that is the entire unlock mechanism.

Two rules that are easy to get wrong:

- `Repository::is_active()` is what the engine should read, not `get()`. It answers false when the
  gate is closed, so a value stored while licensed cannot keep taking effect afterwards.
- **What an element ships with is not gated — only changing it is.** A lapsed licence returns the
  Pix badge to its green pill rather than dropping its background. A storefront should look
  un-upgraded, not broken.

Every default must have a schema field and every schema field a default. `tests/feature-gate-test.php`
enforces both directions, because a default with no field can never be written and sits at that
value forever with nothing reporting it.

## 4. Settings

One option, `wc_custom_installments_settings`. `Settings\Registry` builds the schema — sections →
cards → fields, every label translated in PHP so the payload reaches the browser in the site's
language. `Settings\Repository` reads and writes, sanitizing per declared field type.

The settings **key names are the 5.x ones**, so migrating is a copy rather than a translation
table. `Core\Migrator` imports the 5.x option plus the three sidecar options that held the gateway
rates and the interest table. It never deletes anything it read: a store must be able to roll back
to 5.x and find its data.

### What a product answers to

`Engine\Product_Config` is the one place deciding which discount and which instalment plan a
product gets. Everything that prices a product asks it — the rendered price, the cart total, the
Store API, the storefront runtime's parameters, the Pro add-on's checkout fees — so **never read a
product's discount meta or the plan settings anywhere else**. A rule from outside the product joins
through its two filters, `Product/Discount_Rule` and `Product/Installments_Config`.

Precedence, highest first: the product's opt-outs; the product's own discount (`product_overrides`);
a running campaign; the store's settings.

### Campaigns

A campaign (Pro, `campaigns`) targets products, categories (with their subcategories), tags or
brands, with exclusions and an optional period, and carries a discount, an instalment plan or both.
They are `wcci_campaign` posts — published is active, a draft inactive — with their rules in one meta
key (`Campaigns\Rules` cleans, validates and compiles them).

The storefront never queries them. `Campaigns\Repository` compiles every active campaign that has
not ended into one autoloaded option, the index, on every write; `Campaigns\Resolver` matches against
it through Product_Config's filters and decides whether a campaign is running **from the clock, when
the price is built**. `Campaigns\Scheduler` only exists for copies of a price made earlier: at each
start and end it rebuilds the index and fires `Campaigns/Changed`, which the Pro feed price listens
to. Per effect, the first match in the index's order wins (priority, then the latest start); two
discounts never add up.

## 5. Names that cannot change

These live where nothing can migrate them. Renaming one destroys customer data or content:

| What | Where | What a rename does |
|---|---|---|
| The fifteen `woo_custom_installments_*` shortcodes | Post content | Blanks the element on every page using it |
| The nine `wci_*` Elementor widget names | Inside each saved page | Deletes the widget from those pages |
| Product meta keys | Product meta, on thousands of products | Silently drops the override |
| Storefront CSS classes (`wci-*`, `woo-custom-installments-*`) | Customer stylesheets | Breaks their styling |
| `window.Woo_Custom_Installments`, `woo_custom_installments_ready` | Customer snippets | Breaks their scripts |
| The settings option and its keys | The database | Loses the store's configuration |
| The `wcci_campaign` post type, `_wcci_campaign_rules` and the `wc_custom_installments_campaigns_index` option | The database | Loses every campaign, or leaves them stored but never applied |
| The 54 `Woo_Custom_Installments/…` hooks | Customer `functions.php` | Their snippet stops firing |

Hooks go through `Compatibility\Hook_Aliases`, which fires the current name and the 5.x name on the
same value. **No deprecation notice** — the aliases are supported, not tolerated. A store owner
should not see a warning because we refactored.

New names are added alongside the old. The old ones stay.

## 6. WordPress.org constraints

The free plugin is distributed by WordPress.org, which shapes the architecture more than anything
else:

- **No code executed from a remote server, and no update mechanism of its own.** The MDS SDK lives
  exclusively in the Pro add-on. Never add it here.
- **Nothing contacts an external server before a person asks.** The only outbound request in the
  free plugin is the trial form, which fires when someone fills it in and presses the button — not
  on activation, not on page load, and not at all if the step is skipped. It shows the exact request
  body before sending.
- **Every external service declared in `readme.txt`.**
- **No minified asset without its source**: `app/src` ships alongside `app/dist`.
- GPLv2 or later.

## 7. The admin UI

The settings page and the setup wizard are Vue 3 apps (`app/src`) built by Vite and styled with
Tailwind. They follow the design system MeuMouse shares with **Joinotify** — same tokens, same page
shell, same component shapes — so the plugins read as one family.

### Components only

Pages and feature components are assembled from components. Nothing else renders a control.

- Native controls — `button`, `input`, `select`, `textarea`, `label`, `a`, `form`, `dialog` — appear
  **only inside `app/src/components/base/`**. Anywhere else, use the `Base*` component.
- Layout and text tags (`div`, `span`, `p`, `h1`–`h3`, `ul`, `li`) are fine in any template.
- No `v-html`, no `innerHTML`. Icons are components (`BaseIcon`), not SVG strings.
- A visual pattern used twice becomes a component. A "Pro" pill is `BaseBadge`, a callout is
  `BaseNotice`, a dialog is `BaseModal`.
- `npm run lint:ui` enforces the list above and runs in the build.

PHP renders admin markup only where WordPress or WooCommerce owns it:

- Admin notices go through `wp_admin_notice()`, never a hand-written `<div class="notice">`.
- Product fields use `woocommerce_wp_*`; quick and bulk edit keep the markup WooCommerce's
  inline-edit script expects.
- The view files in `admin/src/Views/` print a mount point and a skeleton, nothing more.
- The storefront stays server-rendered, with no framework: its markup and classes are the §5
  contract and it runs on every product card.

### Tokens

Defined once in `app/tailwind.config.js`, mirrored as `--wcci-*` custom properties in
`app/src/styles/main.css`. Do not hard-code a colour a token already names.

| Token | Value | Used for |
|---|---|---|
| `primary-700` | `#0a8cff` | Buttons, the active tab, switches, focus borders |
| `primary-800` | `#0267bf` | Hover on primary |
| `primary-100` | `#d3e6f6` | Focus ring (`ring-4`) |
| `shell-50` | `#f4f7fb` | Page background |
| `ink` | `#102033` | Headings |
| `slate-*` | Tailwind | Text (800 titles, 500 descriptions), borders (200), dividers (100) |
| `success` / `danger` / `warning` / `info` | `#22c55e` / `#ef4444` / `#ffba08` / `#0ea5e9` | Toasts, notices, badges |

Radius is 8px (`rounded-[8px]`, `rounded-lg`) almost everywhere, full for pills. Field labels are
`text-[15px] font-semibold`, descriptions `text-[13px] text-slate-500`, controls `text-[14px]`.

Tailwind is scoped: `important: '.wc-custom-installments-app'` and preflight disabled, with a small
reset under that class in `main.css`. The WordPress menu, admin bar and notices on the same screen
must never pick up our styles. Anything teleported (modals, listboxes, toasts) goes to the portal
`mountPage()` creates, which carries the scoping class.

### Page shell

Every internal page follows the same structure:

1. **`PageHeader`** — eyebrow with the plugin name, the logo (`BrandMark`, 40px), the page title,
   a description, and an `actions` slot on the right.
2. **`BaseTabs`** (segmented) — one tab per settings section, each with its icon.
3. **`SettingsPanel`** — one white card holding the active section. Each schema card becomes a
   `FieldGroup`; each field a `FieldRow`, label on the left (420px) and control on the right (460px)
   from `lg` up, stacked below it.
4. **`SettingsActionBar`** — sticky inside the panel, never across the viewport.

The logo is `assets/brand/logo.svg`, imported through the `@brand` Vite alias so it ships inside the
bundle. Never build its URL from a hard-coded `/wp-content/plugins/…` path.

A screen of records rather than settings — the campaigns screen, `pages/campaigns/` — follows
Joinotify's list and editor: the list is a panel with state tabs (pill `BaseTabs`), a search and
one row per record, with a switch, icon actions and bulk actions; the editor is the same page with
`?campaign=<id>` (or `new`) in the address, its form built from `FieldGroup`/`FieldRow` and a
summary card beside it. Everything is in memory; each action answers with the fresh list.

### Component catalogue

| Folder | Components |
|---|---|
| `components/base/` | `BaseButton` (renders `<a>` when given `href`), `BaseIconButton`, `BaseIcon`, `BaseInput` (dates too: `type="datetime-local"`), `BaseInputGroup`, `BaseTextarea`, `BaseSelect`, `BaseMultiSelect` (chips over a search the caller supplies), `BaseSwitch`, `BaseCheckbox`, `BaseColorInput`, `BaseFileInput`, `BaseLabel`, `BaseBadge`, `BaseNotice`, `BaseModal`, `BaseConfirmDialog`, `BaseTabs`, `BaseProgress`, `BaseStepper`, `BaseCode`, `BaseForm` |
| `components/brand/` | `BrandMark` |
| `components/layout/` | `PageHeader`, `SettingsPanel` (also the panel of every other page), `SettingsActionBar` |
| `components/fields/` | `FieldGroup`, `FieldRow`, `FieldRenderer`, the field controls and `fieldRegistry` |
| `components/toasts/` | `ToastStack` |
| `components/sections/` | `ExternalSection`, `sectionRegistry` |

Icons come from `@boxicons/vue` through `BaseIcon`, which maps a name to a component. A settings
section names its icon in `Settings\Registry` (`'icon' => 'credit-card'`) — a name, never markup.

### The menu

The plugin has a top-level menu of its own, **Parcelas Customizadas** (`Admin\Menu`). Its slug is the
settings screen's, `wc-custom-installments`, so the first entry reads "Configurações" and the address
5.x-era links and the wizard use keeps working. The icon is `assets/brand/menu-icon.svg`, a
one-colour copy of the logo that WordPress repaints in the admin colour scheme. The 5.x slug,
`woo-custom-installments`, is a hidden page redirecting to the settings screen.

Every screen gates on `$_GET['page']` through `Helpers::current_admin_page()`, never on a hook
suffix: a subpage's hook suffix is built from the *translated* menu title.

### Tabs and screens an add-on renders

A section with a `component` and no cards is drawn as a tab holding a mount point
(`ExternalSection`); the add-on registered under that name in `window.WCCustomInstallmentsSections`
mounts **its own Vue app** there. Never let an add-on hand this app a component instead: it is built
with its own copy of Vue, and a component from another runtime renders with its reactivity silently
cut off. `?section=<id>` opens a tab directly.

A whole screen works the same way. An entry in `WC_Custom_Installments/Admin/Pages` becomes a
submenu drawn by `pages/addon/AddonPage.vue` — the page header and a panel around the same mount
point. The Pro add-on's licence screen is one. The add-on's bundle compiles host components in and
looks their strings up in the host's domain, so the `addon-page` catalogue carries every string under
`components/`, `composables/` and `utils/` (`EXTRA_MODULE_ROOTS` in `languages/js-module-graph.js`).

## 8. Working on it

```bash
cd admin && composer install
cd app && npm install
cd languages && npm install
npm install                    # from the root

npm run build                  # full pipeline → release/wc-custom-installments-<version>.zip
npm run docs                   # regenerate the hook table and the free/Pro page
npm run lint:php               # parses every file with a real PHP 8.1 binary
npm run lint:ui                # no native controls, v-html or innerHTML outside components/base
```

`lint:php` needs a genuine **8.1** binary — linting against a newer runtime accepts syntax the
oldest supported host rejects. Point at one with `PHP81_BIN` in a Git-ignored `.env`.

### Tests

Standalone harnesses. No PhpUnit, no WordPress, no database; any PHP 8.1+ binary runs them.

```bash
php tests/feature-gate-test.php
php tests/migration-test.php
php tests/engine-test.php
php tests/extensions-test.php
php tests/onboarding-test.php
php tests/headless-test.php
php tests/campaigns-test.php
```

Write the expected values **by hand**. The engine harness exists because a rounding change throws no
error anywhere — it quietly charges a different amount on every product in the shop.

### Translations

The source language is **pt-BR** (§0.1). `languages/` holds the `.pot` generated from the source and
one `.po` per bundled locale; the build compiles each into `.mo`, `.l10n.php` and the per-script
`.json` files, which Git ignores.

- **en_US ships in every package** (`BUNDLED_LOCALES` in `scripts/build.mjs`).
  translate.wordpress.org has no English (United States) locale, so no language pack would ever
  bring English; without the bundled catalogue an English-language store reads Portuguese.
- Every other locale comes from translate.wordpress.org. `--ship-locales` packs all the `.po` files
  there are, for installs outside the directory.
- Adding a string: write it in pt-BR, run `npm run pot` in `languages/`, and add its English to
  `wc-custom-installments-en_US.po` (by hand or `translate-cli.js --lang=en_US`). The build does
  not fail on a missing entry, it quietly shows Portuguese to English stores — check the `.po`.
- The copy tokens `{{ parcelas }}`, `{{ valor }}` and `{{ juros }}` stay exactly as written in every
  language: they live in stores' saved settings.

### Previews

`preview.html`, `preview-campaigns.html`, `preview-onboarding.html` and `preview-storefront.html`
render the real built bundles against generated fixtures, with no WordPress. The Pro add-on's
`preview-license.html` renders its licence inside this plugin's add-on page. Regenerate the fixtures with
`php tests/dump-bootstrap.php`, then serve the directory. They have already caught a stale dirty
flag, a stuck CSS transition and a URL builder that threw on a relative base.

### Before finishing a change

- [ ] Every harness passes.
- [ ] `npm run build` produces a package.
- [ ] `npm run lint:ui` is clean: the UI is made of components (§7).
- [ ] `npm run docs:check` is clean if you touched hooks or features.
- [ ] New strings are pt-BR, go through `__()` / `wp.i18n.__`, the `.pot` was regenerated and the
      en_US `.po` has their English.
- [ ] `@since` on new code is the version about to ship; `@version` updated where it exists.
- [ ] `CHANGELOG.md` records what a store owner would notice.
- [ ] Nothing in §5 was renamed.
- [ ] If you commit: English, Conventional Commits, no co-authorship or attribution trailer.
